# 面向「单用户 Jarvis 式个人助理」的差距与改进建议

> 2026-11-01 讨论稿（修订上一份 [super-agent 可行性与必要性](super-agent-feasibility-necessity.md) 的结论口径）。
> 前提（用户确认）：单用户个人助理；**不开放给他人、不接群聊**；任何任务都可能委派；终极目标是类似 Jarvis 的长期运行、接近独立个体的 AI Assistant。
> 依据：本仓库 `.spec/01`–`25`、`packages/*`；DSH `0.2.1-rc.3` 安装闭包；已完成的 [原型分析](analysis-prototype.md)、[现状分析](analysis-nokoribi.md)、[映射分析](analysis-mapping.md)。

## 0. 结论

1. **你的场景恰好是知乎文章 2.2 节「个人助手」变体**：单一对话入口维持连续性（Router），后端按话题/任务分派 Worker。所以双层架构从「团队场景的过度设计」变成**长期演进方向**，但前提是先有「任务」和「事件」这两个输入，以及「可靠触达」这个输出。
2. **单用户把 super-agent 最重的部分全部省掉**：不需要 Policy/Mandate/多用户准入矩阵、不需要跨信道多人一致、不需要团队任务板。剩下真正该吸收的是：**任务化双层、事件驱动、全双工、Inline & Spill、链式召回、Watchdog、脑手分离**。
3. **但当前最该补的不是双层，而是四个地基**：① 任务对象（委派出去的东西不能丢）；② 可靠主动触达（Jarvis 必须能主动找到你）；③ 记忆的长期性（多年连续、不遗忘、不混淆）；④ 无人值守下的自主权/审批模型。没有这四样，双层只是把单会话拆开，收益有限。
4. **即时可做的小项**：开启 spill（现在实际是关的）、`/clear` 前记忆提炼、每日简报（schedule）、delegation 纪律。这些是 S 级、不改变架构。

## 1. super-agent 设计：对你的目标该怎么取舍

| 文章机制 | 对你的目标 | 建议 |
| --- | --- | --- |
| 双层架构（Router + Worker） | **采纳，但渐进**：主会话 = 助理（对话、意图、分派、汇报、澄清），任务 = 后台 Worker（隔离上下文、可并行、可恢复）。不必立刻让主会话"不能干活"；先结构化长任务的委派。 | 先做任务域 + 软双层（长任务必须进 Worker，短任务主会话直接做）；等任务量上来再考虑严格 Router 工具限制 |
| 事件驱动（Trigger/Thread/Ticket） | **采纳核心，砍掉授权层**：Source → Trigger → 任务/通知；程序规则 Fast Path + LLM 注意力 Slow Path。单用户不需要 admission 矩阵/Mandate/Policy 版本，只需要「规则 + 安静时段 + 打扰分级」。 | 事件源先做 1–2 个高价值源（日程、邮件、GitHub/CI、系统/文件）；Thread 简化为「任务/话题」 |
| 3.1 两级过滤 | **采纳**：大部分事件用确定性规则丢掉；只有候选才让模型判断"值不值得打扰、要不要行动"。 | 见 P0-3 |
| 3.2 订阅直通 | **简化为任务绑定**：后续消息路由到对应任务的 Worker，而不是 Router 转发。单用户多对多订阅无意义。 | 跟随任务域一起做 |
| 3.3 Inline & Spill / 链式召回 | **采纳**：先开 spill；任务/记忆/会话都带 ID，形成可按需展开的引用图（任务→会话→记忆→相关任务）。 | spill 一行配置；引用图作为任务域的副产品 |
| 3.4 投机执行 | **改为「观察→建议→自动」三档**：先用 observe 记录"我本来会做什么"，校准你的信任边界，再放开 auto。 | 非常适合单用户校准主动边界，见 P0-3 |
| 4.1 全双工 | **采纳，且基础已有**：`run_in_background` + DSH jobs + 完成唤醒；缺口是"前台长命令自动转后台"（D135 明确不用）与提示词纪律。 | 评估 D135 改为可配（默认关闭不影响现状） |
| 4.2 多信道 | **不需要多人/群，但需要多触达点**：不同设备/入口（IM、邮件、桌面通知、语音）统一到同一 Agent。 | 见 P0-2（这是 Jarvis 的硬前提） |
| 5 计算/状态/环境分离 | **不适用**：你的 Agent 已常驻服务器，持久性由 systemd + resume 解决。只有"脑手分离"的简化版有意义：服务器上的 Agent 通过 SSH/端侧 daemon 操作用户自己的机器。 | 见 P2-8 |
| 6 Watchdog | **采纳，简化**：任务级巡检（停滞/偏航/预算超限）+ 自维护（备份、清理、健康）；不需要形而上学的"独立 Watchdog Agent"，用 schedule + 只读检查 + 系统通知即可。 | 见 P1-7 |

## 2. 需要改进的地方（按优先级）

### P0-1 任务域与双层调度（"任何任务委派"的地基）

**现状**：`goal` 是长期多轮目标（有 goal 状态、冷恢复、归档、报告转述），`subagent` 是一次性委托；两者对用户基本不可见（只有 `/goal list`），没有统一的任务列表、任务状态、任务工作目录/产物、任务级后续消息路由。主会话仍然亲自执行大部分工作（`.spec/10`、`.spec/05`）。
**目标**：引入 **Task（任务）** 作为一等对象：
- 用户说"帮我做 X" → 助理创建 Task（可绑定 Worker 会话、工作目录、授权范围、预算），后台推进；
- Task 有生命周期（created/running/waiting/reported/done/failed/cancelled）、报告、产物、归档；
- 你可以 `查看/追问/暂停/取消/重试` 任务；后续相关消息路由到该任务的 Worker；
- 主会话保留对话连续性，不承担长时间执行。
**最小动作**：先复用 `GoalManager` 扩展出 TaskManager（child 生命周期、冷恢复、归档已有约 70%），加任务列表命令与报告转述；不引入 experimental 包。可先做 1–2 天 spike 验证 DSH experimental Agent Team（它提供 Lead + teammate + durable task board），但它在 rc.3 是 experimental、且会替换 `send_message` 等工具名、与 goal 生命周期冲突——**适合参考/试用，不适合直接生产**。
**成本**：M（先 spike 后实施）。

### P0-2 可靠的主动触达（Jarvis 的硬前提）

**现状**：QQ 官方 Bot 主动推送自 2025-04-21 下线；被动回复窗口单聊 60 分钟/4 次、群 5 分钟/5 次；提醒/通知在无法 active 时 defer 到下一次入站（D161，`.spec/17:76-78,201-218`）。这在当前是"聊天机器人"的合理取舍，但对 Jarvis 是硬伤：**你不在 QQ 说话，它就找不到你**。
**目标**：至少一个可靠、可主动推送的触达通道 + 通知策略：
- 通道：邮件（最稳）、Telegram/企业微信/飞书、ntfy/自建推送、或桌面/手机 App；QQ 保留为对话入口之一；
- 通知分级：立即 / 摘要 / 静默（只记账）；安静时段；去重与合并；
- 投递兜底：主通道失败降级到备通道，而非永久 defer。
**明确决策**：如果坚持 QQ-only，就必须接受"主动能力最长延迟到下次你发消息"，那么 Jarvis 的"主动"只能做到"下次对话时告诉你"。
**成本**：通道实现 S–M（channel-core 已有 driver 抽象），短信/推送服务运维另计。

### P0-3 事件源与注意力策略（从"提醒"到"主动"）

**现状**：只有 schedule 提醒（`schedule_create` 等，最小 60s，主会话独享）；没有事件源、没有心跳/周期检查（D62）、没有语义级事件过滤（`.spec/10:157-168`）。
**目标**：个人助理版的事件驱动：
- 事件源：日程/待办、邮件、GitHub/CI、系统健康与文件变化、新闻/RSS、设备上线等；先做 1–2 个最有价值的；
- 两级过滤：程序规则（来源/时间/关键词/去重/安静时段）→ 候选事件；LLM 注意力判断（是否值得打扰、要不要行动、以什么形式）；
- 三档主动模式：**observe（只记录"本来会做什么"）/ suggest（提醒你）/ auto（直接做）**，按规则/场景逐步放开——这是文章 acceptMode 的单用户版，也是校准信任的最佳工具；
- 打扰预算与静默默认（"不说废话"应作为硬规则写进提示词）。
**成本**：M–L（取决于事件源数量与推送通道）。

### P0-4 记忆系统 v2（多年连续性的核心）

**现状**：`memory` 工具 + pinned 快照自动注入（M16，默认 3000 字符/20 条）+ session FTS5 检索（M11）；提炼子代理只在 goal 完成/阻塞时触发（`.spec/09:138,157-171`）；`/clear` 不继承摘要（D17）；无向量/embedding（D143，OpenViking 可选）。**这只能支撑"短期助理"，支撑不了"多年个体"。**
**目标**：
- **自动提炼**：不只 goal 终态；显著任务完成、重要对话转折、`/clear` 前都提炼；低价值不写；
- **整合与遗忘**：合并重复、supersede 旧事实、置信度/时效、定期"记忆整理"（可用 schedule 每日/每周一次低成本运行）；
- **检索增强**：按当前任务/话题召回相关记忆注入（现在只注入 pinned 快照），避免"知道但想不起来"；
- **画像与项目记忆**：你的偏好、习惯、重要人/项目/决定，长期稳定、可审计、可纠正；考虑向量检索或 OpenViking 后端（M17 已铺路）；
- **记忆卫生**：来源、置信度、过期标记、敏感信息规则（现状有 secret guard，但可强化）。
**成本**：M–L，建议分两期（先自动提炼+整合+`/clear` 前提炼，再考虑向量/图谱）。

### P1-5 自主权与审批模型（无人值守的关键）

**现状**：每个工具调用先过 fast→strong LLM reviewer；deny/不确定才走 IM 单次授权（当前 60s 超时即拒绝，fail closed）；审批 broker 全局串行（`.spec/05:130-138`、`.spec/08`）。这对"你在线"没问题，对"Jarvis 自己跑长任务"是瓶颈：你不在时，多数敏感动作会被拒；多个任务并发时审批排队。
**目标**：风险分级的自主权：
- 只读/搜索/无害动作免审或策略放行；
- 任务创建时授予"任务级授权"（这个任务允许写哪些目录/执行哪些命令），任务内不再逐次问；
- 高风险（sudo、删除、外发、付款）仍逐次审批，但支持 **defer/稍后审批**（你回来后一次性处理，而不是 60s 过期拒绝）；
- 审计：谁在何时授权、任务做了什么，可追溯。
**成本**：M（涉及 vendor reviewer 与 broker，安全审查重；`.spec/04` 的 vendor 规则要求同步 PATCHES/VERSION）。

### P1-6 成本与模型治理

**现状**：单 provider（DeepSeek API key）；主模型/goal/reviewer 路由在 Nix 固定；无 token 预算（D70）；无模型 fallback、无 `/model` 切换（`.spec/11`）。长期运行 + 多任务 + 事件驱动会把成本放大。
**目标**：
- 日/任务 token 或费用预算，超预算降级（换便宜模型/暂停任务/通知你）；
- 模型分工：主会话（对话/路由）可用较快模型，Worker（执行）用强模型，reviewer 独立；失败/限流自动 fallback；
- 可观测：`/cost`、每日简报里带用量；
- 成本与自主权联动：任务级预算 + 超限行为。
**成本**：M。

### P1-7 可靠性与自维护

**现状**：systemd 存活 watchdog + 崩溃恢复 + goal 冷恢复 + outbox 重发；**无备份/回滚**（D105/D84 接受）、**无任务级 watchdog**、无日志/存储清理策略、升级直接进行（D110）；持久终端跨重启不保留。
**目标**：
- 任务级巡检：卡住/空转/偏航/超预算的任务检测与介入（schedule 驱动，先 MVP 通知）；
- 备份与恢复：`$DSH_HOME`（sessions/state/memory）定期快照，至少手动恢复流程；
- 升级安全：升级前备份、升级后自检、失败回滚；
- 清理：session/沙箱/日志/索引的保留策略；
- 健康简报：每日一次"我做了什么/遇到什么/需要你什么"。
**成本**：M。

### P2-8 执行环境扩展（脑手分离的简化版）

**现状**：local/sandbox 双 host 都在服务器本机；SSH host 后置未排期（`.spec/14:366-382`）；持久终端进程内、重启丢失；无远程文件工具。
**目标**（按需）：能操作你自己的其他机器——SSH host / 端侧轻量 daemon；持久终端跨重启（tmux/screen 重新附着）；远程 read/write/edit。这是"帮我处理我电脑上的事"的基础。
**成本**：M–L。

### P2-9 交互与可观测性

**现状**：只有 IM 命令（`/stop /status /clear /new /goal …`）、`/status full` 与 journald；无 Web UI（R1 有意为之）；无任务列表/每日简报/面板。
**目标**：先做 IM 命令面（`/tasks`、`/task`、`/memory`、`/cost`、`/brief`），每日简报；如果确实需要，再评估"最小只读 Web 面板"（这会与 R1「精简 DSH / 无 Web UI」冲突，需要你拍板）。
**成本**：S–M。

### P2-10 能力广度与人格

**现状**：bash/终端/文件/Web/技能/MCP/图片/文件/schedule/memory/session search 已具备；无浏览器自动化、无语音、无日历/邮件/家庭自动化开箱集成；人格由 SOUL.md 定义。
**目标**（按需）：浏览器自动化（动态网页/登录态）、日历/邮件/待办通过 MCP、语音（可选）、以及"什么时候可以主动打扰你"的边界写入人格与规则。
**成本**：按能力计。

## 3. 建议顺序（Jarvis 化三步）

**第一阶段「可靠的助理」**（先做，S–M）：
- 开 spill（一行配置；现在实际禁用）；
- `clear` 前自动记忆提炼 + `/tasks` 只读（读 goal/任务状态）；
- 每日简报（schedule）+ delegation 纪律（长任务 `start_goal`、长命令 `run_in_background`）；
- P0-1 任务域 spike + 最小 TaskManager。

**第二阶段「主动的助理」**（P0-2 + P0-3，M–L）：
- 先加一个可靠主动通道；再把 schedule 升级为事件源 + 两级过滤 + observe/suggest/auto 三档；
- 用 observe 模式积累"它会做什么"的记录，校准后再放开。

**第三阶段「自主的个体」**（P1 + P2，M–L）：
- 自主权/审批模型、成本预算、任务级 watchdog 与备份；
- SSH/端侧环境、能力广度（浏览器/日历/邮件）、交互面与人格收敛。

**不建议现在做**：严格 Router（主会话禁止 bash/写）、团队任务板、多用户/群聊相关设计、移植 dsh-superagent 原型（Web 硬依赖、GitHub 场景写死、danger-full-access 与 Auto review 冲突）。

## 4. 需要你确认的问题

1. **触达通道**：QQ-only 并接受主动延迟，还是加一个支持主动推送的自有通道（邮件/Telegram/ntfy/自建）？这决定"主动"能否成立。
2. **任务模型**：是否要"用户可见的任务列表 + 后台 Worker + 报告"？以及你接受主会话把长任务全部移交、短任务仍直接做吗？
3. **自主权**：默认授权级别怎么定（只读免审？写操作任务级预授权？sudo 逐次？）；是否允许"稍后审批"而不是 60s 拒绝？
4. **成本**：日/月预算上限；超预算行为（降级/暂停/只通知）。
5. **记忆野心**：先增强事实库+自动提炼+检索（S–M），还是直接上向量/OpenViking/知识图谱（M–L）？
6. **观测面**：坚持 IM-only（命令 + 简报），还是允许最小只读 Web 面板（与 R1 冲突）？
